# ADR-0008: Base de implementação da GSDM 0.1.0

- Status: Aceita
- Data: 2026-10-25

## Contexto

ADR-0001, 0002 e 0007 definem *o que* a GSDM é. Faltavam as escolhas
concretas para a primeira versão executável, incluindo a decisão em
aberto da ADR-0002 (linguagem-alvo do parser).

## Decisão

### Escopo e dependências

1. **Linguagem-alvo do GVF 0.1.0: Python.** O parser usa o módulo `ast` da
   stdlib — sem dependência externa e com AST oficial da linguagem.
2. **Dependência de runtime única: NumPy.** Sem PyTorch/TensorFlow/JAX. A
   GSDM implementa o próprio autograd (diferenciação automática
   reverse-mode) sobre arrays NumPy, em `float64`.
3. **Dois pacotes no mesmo repositório:**
   - `gsdm` — a arquitetura de treinamento, genérica: não sabe o que é
     Python, vulnerabilidade ou XML. Qualquer modelo pode ser treinado
     sobre ela a partir de um grafo estrutural.
   - `gvf` — o produto (Clean Architecture, ADR-0003). Do ponto de vista
     do GVF, a GSDM é um detalhe de infraestrutura atrás do port
     `VulnerabilityDetector`.

### Arquitetura do modelo

4. **Grafo estrutural heterogêneo:** nós com vetor de features e N tipos
   de relação (arestas tipadas). A agregação de mensagens é esparsa
   (O(arestas)), com média por grau de entrada de cada relação.
5. **Codificação de entrada:** `h₀ = tanh(X·W_in + b)`.
6. **Passo de raciocínio (ADR-0007):** um único bloco com **pesos
   compartilhados** aplicado N vezes:
   `h ← LayerNorm(h + ReLU(Σ_r propagate_r(h)·W_r + h·W_self + b))`.
   Pesos compartilhados tornam cada rodada o *mesmo* passo de raciocínio
   repetido, então N pode variar na inferência (base para o N adaptativo
   da v2). Conexão residual + LayerNorm mitigam over-smoothing.
7. **Readout por atenção por categoria:** para cada categoria, uma
   distribuição de atenção sobre os nós (softmax sobre nós), um embedding
   do grafo ponderado por essa atenção, e um logit. Isso **não** é
   self-attention de transformer (nós não atendem uns aos outros); é
   pooling. O nó de maior atenção é a **localização** do achado —
   localização fracamente supervisionada, sem precisar de rótulo por linha.
8. **Treino:** binary cross-entropy multi-rótulo com logits, Adam,
   clipping de norma global de gradiente, mini-batches por acumulação de
   gradiente, seeds fixas. É o mesmo regime de otimização usado em modelos
   transformer — a diferença está no que é otimizado, não em como.

### Features do GVF para Python (versão de schema 1)

9. Por nó do AST: tipo do nó (one-hot sobre vocabulário fixo; contexto e
   operadores como `Store`/`Add` viram features do nó pai, não nós
   próprios), subtokens de identificadores em 256 buckets via hash
   CRC-32 (estável entre execuções — o `hash()` do Python não é), e
   estatísticas de strings literais (tamanho, entropia, proporções de
   classes de caracteres). São *sinais*, não regras: quem decide é o
   modelo treinado.
10. Relações (6): filho/pai no AST, próximo/anterior no fluxo sequencial
    de statements (CFG simplificado), definição→uso e uso→definição de
    nomes por escopo (DFG simplificado).
11. A versão do schema de features e a ordem das categorias são gravadas
    no arquivo do modelo e verificadas no carregamento. Um modelo treinado
    com features diferentes é recusado, nunca usado em silêncio.

### Persistência

12. Modelo salvo em `.npz` com `allow_pickle=False` na leitura. Um
    detector de deserialização insegura (VC-2) não pode ele mesmo
    deserializar pickle de um arquivo de modelo.

### Treino como detalhe de infraestrutura

13. O pipeline de treino vive em `gvf/infrastructure`, não como use case:
    treinar não é regra de negócio da análise de vulnerabilidades, é como
    o detalhe "detector" é produzido.

## Limitações conhecidas da 0.1.0 (assumidas)

- CFG sem ramos/laços reais (apenas sequência de statements).
- DFG por ordem de posição no fonte, sem análise de alcance completa.
- Sem análise entre arquivos (cada arquivo é um grafo isolado).
- Sem pesos treinados distribuídos: não há dataset rotulado em Python
  no repositório ainda. A 0.1.0 entrega a arquitetura e o pipeline
  verificados; o GVF útil depende do dataset (próximo marco).
- MCP (ADR-0006) fica para a 0.2.0; a 0.1.0 expõe uma CLI.

## Consequências

- Positivo: zero dependência de framework de ML; cada operação tem
  gradiente verificado numericamente nos testes.
- Negativo: NumPy puro em `float64` é mais lento que um framework com
  kernels otimizados; aceitável para o tamanho de grafo de um arquivo.
